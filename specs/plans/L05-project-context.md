**Assumptions:**
(1) Work happens on `feature/sdd-agents` (base `origin/main` `1445e4d`). The amended spec files are uncommitted in the working tree. Paths are relative to the repository root.
(2) The clone-file port is declared in the adapter's own `src/adapters/clone-files/index.ts`, as `Tokenizer`, `DepGraph` and `HttpFetcher` are. The module declares the same shape structurally in its own `ports.ts`. Neither side imports the other, because an adapter may not import a module and a module may not import an adapter.
(3) A search-root folder name matches exactly (case-sensitive). The `.md` extension matches in any case.
(4) "Sorted by path" means JavaScript's default code-unit order (`a < b`), as `walk.ts:63` uses, on the server and in the client.
(5) The run reads every effective path once. A path that misses keeps its own reason. The 16,000-token cap is applied in order over the readable, non-empty documents only.
(6) In the list route, a document whose read answers `not_found`, `outside_clone` or `not_cloned` after the walk listed it (a race) is left out of the list.
(7) Checking a document in a Context tab appends it to the end of the attached list.
(8) The Live Log origin text is `(agent)` or `(skill <name>)`.
(9) `specs_loaded` and `specs_skipped` are written as `null` when empty, like `skills_loaded`. `specs_tokens` and `specs_calls` are `null` when the run sent no section.
(10) The agent Context tab heading is "Project context". The skill Context tab heading is "Project context to use" (R-WEB-18).
(11) If `container.projectContext.forRun` throws (for example on a database error), the run logs `Project context: unavailable (<message>)` at `info` and continues without project context (NFR-6).
(12) A failed save is toasted by the global `MutationCache.onError` (`client/src/lib/providers.tsx:41-42`); the Context tab adds no second toast.

## Constraints
- **Architecture:** a module never imports another module, `import type` included. The `reviews` run therefore reaches project context only through `container.projectContext`, built in `container.ts` the way `container.intent` is. The run uses its type as `Container['projectContext']` — `server/.dependency-cruiser.cjs:66-73`; `server/INSIGHTS.md:97-102`; `server/src/platform/container.ts:111-122`.
- **Architecture:** an adapter never imports a module (`adapter-no-app-layers`, `server/.dependency-cruiser.cjs:91-96`). The `CloneFiles` port therefore lives in the adapter's own `index.ts`, and the module repeats it structurally in `ports.ts` — `.claude/skills/onion-architecture/references/adapters.md:19-27`; precedent `server/src/adapters/mocks.ts:38` (`HttpFetcher`).
- **Architecture:** only `repository.ts` imports `src/db/`. Only `routes.ts` imports Fastify and reads `app.container`. `service.ts` takes narrow dependencies and never the `Container`. `domain.ts` and `ports.ts` import nothing but `@devdigest/shared` — `server/.dependency-cruiser.cjs:18-27`, `:52-64`, `:75-89`.
- **Architecture:** the service decides the transaction. A `PUT` runs through a unit of work, as in skills — `server/src/modules/skills/repository.ts:135-137`; `onion-architecture` `db-tx-owned-by-use-case`.
- **Architecture:** `platform/config.ts` may not import a module (`platform-no-modules`, `server/.dependency-cruiser.cjs:97-103`). The default search roots therefore live in `config.ts`.
- **Architecture:** validation is schema-first. Body and params are declared on the route, and an invalid body is a `422` before the handler runs. The file route's `path` query is a plain `z.string()` so that a bad path is a `404` from the service (R-SRV-36) — `server/CLAUDE.md`, Conventions.

export type CloneFileMiss = 'not_found' | 'too_large' | 'unreadable' | 'outside_clone';
export type CloneListResult = { kind: 'not_cloned' } | { kind: 'entries'; entries: CloneFileEntry[] };

## Risks
- NFR-1 may miss its 2,000 ms target, because every list request reads and counts every document and nothing is cached by decision. The manual measurement in phase 6 records the figure; a miss becomes a user decision (Open questions), not a silent cache.
- The client copy of `@devdigest/shared` has already drifted, so a whole-file sync could change unrelated types. Phase 2 edits only the two named regions in each copy.
- Integration files can skip silently and look green. Every server `Verify (phase)` is read for `skipped`; on a skip, the `.it` lane is rerun alone with `--no-file-parallelism` (`server/INSIGHTS.md:218-239`).
- The save-coalescing hook could race (a lost update or a double send). Its logic sits in one hook with a dedicated test: three quick saves give two `PUT`s, and a failure restores the confirmed list.
- `run-executor.ts` grows again. Everything except calling, logging and tracing stays in `container.projectContext`, and the run change is limited to one call, the log lines and five trace fields.
- The tokenizer change alters counts only for texts that contain special-token markers; before this change those texts threw and switched the process to the chars/4 heuristic. `server/test/repo-intel-rank-map.test.ts` keeps covering the ordinary path.
- The hermetic e2e run shares `client/.next` with a running dev server. Phase 11 stops the dev server or runs from a worktree (`e2e/INSIGHTS.md:87-103`).

## Open questions
- If the phase 6 measurement exceeds NFR-1 (2,000 ms for 1,000 documents), there are three options: (a) accept the figure and record it; (b) bring back an in-process token-count memo, which is a spec change through `spec-creator`; (c) relax NFR-1 in the spec. I would pick (a) when the miss is small and typical repositories hold far fewer documents, and (b) otherwise.
