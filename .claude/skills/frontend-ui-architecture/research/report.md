# Colocate first, promote on reuse, enforce with lint

No official source prescribes a React or Next.js folder layout. Both frameworks call themselves unopinionated and tell teams to pick one structure and keep to it. The rules that do hold across sources are narrower. **Keep code next to its only consumer, and move it up only when a second real consumer appears.** **Keep dependencies one-way (shared → features → app), and never import feature to feature.** **Split components when a concrete problem appears, not in advance.** **Keep domain rules in plain functions, React wiring in hooks, and server data in a server-state cache, never copied into React state.** Those four principles cover every placement question in scope: components, constants, utils and helpers, business logic, and state. The real disputes are about barrel/`index.ts` files, feature-based versus type-based folders, file-name case, and `enum` versus `as const`. On each of these, recognised experts contradict each other, so a skill should present its choice as a project convention rather than a universal rule. DevDigest's client layout (`src/app/**/_components/<Name>/` with `Name.tsx`, a one-line `index.ts`, `constants.ts`, `helpers.ts`, `styles.ts` and a colocated test, plus `src/lib/hooks/<resource>.ts` → `src/lib/api.ts`) matches the official Next.js "split by feature or route" strategy and has direct expert backing. Several of its details are house conventions, though, and the skill should label them as such. The last section of this report is a deduplicated catalogue of **about 110 sources**, graded and tagged by the questions they answer. It is written to become the skill's README sources section.

## Official docs leave structure open; the community fills the gap with colocation

**React's only official statement on file structure is the archived legacy FAQ.** It lists grouping "by features or routes" and grouping "by file type", notes that most teams end up with a hybrid, suggests limiting nesting to three or four folders, and advises: "Don't spend more than five minutes on choosing a file structure" ([React legacy FAQ](https://legacy.reactjs.org/docs/faq-structure.html)). Current react.dev has no replacement page. Dan Abramov's canonical one-liner is "move files around until it feels right", followed by "this is not a joke" ([react-file-structure.surge.sh](https://react-file-structure.surge.sh/)). **Next.js (docs v16.3.6, updated 2026-07-21) is explicitly "unopinionated" about the same question.** It offers three strategies: project files outside `app/`, top-level folders inside `app/`, or "split project files by feature or route". It also says the `components` and `lib` names have "no special framework significance" ([Next.js project structure](https://nextjs.org/docs/app/getting-started/project-structure)).

The Next.js page does settle the mechanics of colocation. Nothing in `app/` is routable until it contains a `page` or `route` file, so project files "can be safely colocated". **`_private` folders opt a whole subtree out of routing.** Their documented purposes include "Separating UI logic from routing logic" and avoiding clashes with future file conventions. The page's own example is `app/blog/_components/Post.tsx` ([Next.js project structure](https://nextjs.org/docs/app/getting-started/project-structure)). DevDigest's `app/**/_components/` combined with a shared `src/lib/` is therefore a combination of official strategies 3 and 1, using the officially recommended folder name.

Community reference architectures push further. **Bulletproof React** (about 36k stars) uses `src/{app, assets, components, config, features, hooks, lib, stores, testing, types, utils}`. Features hold only the subfolders they need: `api`, `components`, `hooks`, `stores`, `types`, `utils`. Imports run strictly "shared → features → app", and features never import each other: "compose different features at the application level" ([Bulletproof project-structure](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). Its Next.js variant keeps UI outside `app/`, which is official strategy 1 ([Bulletproof nextjs-app/src](https://github.com/alan2207/bulletproof-react/tree/master/apps/nextjs-app/src)). **Feature-Sliced Design** formalises the same idea as layers: app > pages > widgets > features > entities > shared. Each layer holds slices, and each slice holds `ui/api/model/lib/config` segments. A module may import only from layers strictly below it, and every slice exposes an index public API ([FSD overview](https://feature-sliced.design/docs/get-started/overview)). Adopting FSD in Next.js means renaming FSD's layers to `_app`/`_pages` and keeping route files as bare re-exports ([FSD with Next.js](https://feature-sliced.design/docs/guides/tech/with-nextjs)). That directly conflicts with colocating `_components` inside route segments. Practitioners also report a steep learning curve and a client/server barrel problem: "if server components and client components are exported by a single file, the server components are marked as client components" ([Chan, dev.to 2024](https://dev.to/algoorgoal/feature-sliced-design-review-22k0)).

**Robin Wieruch's size-driven progression is the most useful tie-breaker.** It runs from a single file, to a folder per component, to technical folders (`components/`, `hooks/`, `utils/`, `lib/`) for mid-size apps, to `features/` for large apps, with domain folders once `features/` passes about ten entries. Code "flows in one direction... never the other way around" ([Wieruch](https://www.robinwieruch.de/react-folder-structure/)). **Josh Comeau is the named dissenter.** He organises "by function, not by feature" because "categorization is actually really hard" ([Comeau](https://www.joshwcomeau.com/react/file-structure/)). **Kent C. Dodds supplies the principle every camp accepts:** "Place code as close to where it's relevant as possible" and "Things that change together should be located as close as reasonable". Tests and styles sit next to their component, and central `utils/` folders collect orphaned code ([Kent C. Dodds, Colocation](https://kentcdodds.com/blog/colocation)). No source offers quantitative evidence comparing layouts. Every position above is expert judgement.

Inside a component folder, Comeau and Wieruch converge on a folder per component, with an `index` entry point and sibling helpers, constants, types and tests. Comeau names the siblings with dot notation (`Widget.constants.ts`, `Widget.helpers.ts`) and uses only `export { default } from './FileViewer'` in App Router projects ([Comeau](https://www.joshwcomeau.com/react/file-structure/)). Wieruch keeps a hook that serves one component inside that component's folder, and moves hooks to `hooks/` only once they are reused ([Wieruch](https://www.robinwieruch.de/react-folder-structure/)). Nesting limits differ by source: three or four levels (React FAQ), two (Wieruch), or a structural three (FSD's layer/slice/segment).

## Split components on a concrete trigger, and let the client boundary cut the tree

**react.dev's rule is one concern per component, decomposed as it grows**, with the design and the data model suggesting the hierarchy ([Thinking in React](https://react.dev/learn/thinking-in-react)). Several small, tightly related components may share a file ([Your First Component](https://react.dev/learn/your-first-component)). **Kent C. Dodds adds the counterweight that should drive a skill's trigger list.** Split when you hit a real problem: re-render cost, a need for reuse, state that is hard to follow, tests that are hard to isolate, merge conflicts, or wrapping an imperative API. "NOT BEFORE." He quotes Sandi Metz: "Duplication is far cheaper than the wrong abstraction" ([Dodds, When to break up a component](https://kentcdodds.com/blog/when-to-break-up-a-component-into-multiple-components)). Premature splitting "unnecessarily aggravates prop drilling" ([Dodds, Prop Drilling](https://kentcdodds.com/blog/prop-drilling)). **No authoritative source gives a line-count or prop-count threshold**, so any numeric limit in the skill is a house rule. Dan Abramov turns splitting into a performance tool. "Move state down" extracts the part that changes, and "lift content up" passes the static part as `children`. Try both before reaching for `memo` ([Before You memo()](https://overreacted.io/before-you-memo/)).

The container/presentational split is obsolete by its author's own account. **In 2019 Abramov added a note to his 2015 article: "I don't suggest splitting your components like this anymore"**, because hooks separate stateful logic "without an arbitrary division" ([Abramov, Presentational and Container Components](https://medium.com/@dan_abramov/smart-and-dumb-components-7ca2f9a7c7d0)). patterns.dev agrees ([patterns.dev](https://www.patterns.dev/react/presentational-container-pattern/)). Today the "container" role belongs to a custom hook on the client, or to a Server Component that fetches data and passes props to interactive leaves ([Next.js Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)).

For composition, react.dev prescribes an order of preference. Pass props first. Then "Extract components and pass JSX as `children`", because intermediate components that only forward data mean "you forgot to extract some components along the way". Only then use context, for theme, current account, routing or reducer-backed state ([Passing Data Deeply with Context](https://react.dev/learn/passing-data-deeply-with-context)). Compound components share implicit state through context ([Dodds, Compound Components](https://kentcdodds.com/blog/compound-components-with-react-hooks)). Headless components are hooks that supply "the brains" while the consumer supplies "the looks" ([Qiu, Headless Component](https://martinfowler.com/articles/headless-component.html)).

**The App Router adds a decomposition axis that older sources lack.** Put `'use client'` on small interactive components "instead of marking large parts of your UI as Client Components". Everything a client file imports ships to the browser. Server UI crosses into client components through `children` slots, and providers should render "as deep as possible" ([Next.js Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)). One sharp edge matters for folder conventions. **Compound subcomponents attached as static properties (`Menu.Item`) become `undefined` when a Server Component imports them. Expose them as named exports instead** ([Next.js Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)). Two rules are non-negotiable. Components must be pure ([Keeping Components Pure](https://react.dev/learn/keeping-components-pure)), and "you must never nest their definitions", because a nested definition creates a new component type on every render ([Your First Component](https://react.dev/learn/your-first-component)). React's lint preset now flags the second rule automatically through `static-components` and `component-hook-factories` ([eslint-plugin-react-hooks](https://react.dev/reference/eslint-plugin-react-hooks)).

## Constants, helpers and types stay local until a second consumer appears

**No official source defines a `constants/` folder, and none distinguishes "helper" from "util".** Both distinctions are conventions. The sources that do speak agree on colocation plus promotion. Bulletproof has a top-level `config/` for "global configurations and environment variables" and no per-feature constants folder ([Bulletproof project-structure](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). FSD gives every slice a `config` segment and keeps environment variables and flags in `shared/config` ([FSD slices-segments](https://feature-sliced.design/docs/reference/slices-segments)). DevDigest's per-component `constants.ts` is colocation at the smallest scale. It breaks no cited rule, but no T1 or T2 source names it either. For typed constant sets, **`as const` objects beat `enum`.** The TypeScript handbook says "you may not need an enum when an object with `as const` could suffice" ([TS Handbook: Enums](https://www.typescriptlang.org/docs/handbook/enums.html)). Matt Pocock objects to enums' reverse mappings and nominal typing ([Pocock](https://www.totaltypescript.com/why-i-dont-like-typescript-enums)). TS 5.8's `erasableSyntaxOnly` turns enums into errors ([Pocock, erasableSyntaxOnly](https://www.totaltypescript.com/erasable-syntax-only)). **Google's style guide is the dissent.** It bans only `const enum`, and it reserves `CONSTANT_CASE` for module-scope constants ([Google TS Style Guide](https://google.github.io/styleguide/tsguide.html)). One Next.js rule traps people who centralise configuration. `NEXT_PUBLIC_` values are inlined at build time, and dynamic lookups such as `process.env[name]`, or destructuring `process.env`, are "NOT inlined". **A client `config/env.ts` must therefore read each variable by literal property access** ([Next.js environment variables](https://nextjs.org/docs/app/guides/environment-variables)).

On utilities, Bulletproof separates `lib/` ("Preconfigured reusable libraries") from `utils/` ("Shared utility functions"), and a feature may have its own `utils` ([Bulletproof](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). **FSD rejects the dumping ground outright.** It says `shared/lib` "should not be treated as helpers or utilities", that every module in it needs "one area of focus", and that names like `components`, `hooks` and `types` are "bad segment names" ([FSD layers](https://feature-sliced.design/docs/reference/layers)). Dodds's AHA principle ("prefer duplication over the wrong abstraction", "Optimize for change first") backs the promotion rule: stay local, then move to the nearest common ancestor once the code is genuinely shared ([Dodds, AHA Programming](https://kentcdodds.com/blog/aha-programming)). AHA deliberately refuses a fixed threshold, so "promote on the second use" versus "on the third" is a judgement call. React draws the helper/hook line precisely: **a function that calls no hooks must not take the `use` prefix** (`getSorted`, not `useSorted`) ([Reusing Logic with Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)).

Types follow the same pattern. Keep them in ordinary `.ts` files next to their use. Pocock warns that hand-written `.d.ts` files are silently skipped by `skipLibCheck`, and that `declare global` produces "a mess of implicit dependencies" ([Total TypeScript Essentials](https://www.totaltypescript.com/books/total-typescript-essentials/modules-scripts-and-declaration-files)). For contract types, Zod's own documented pattern gives the schema and the inferred type one name: `const Player = z.object(...)`, `type Player = z.infer<typeof Player>` ([zod.dev](https://zod.dev/basics)). That is exactly DevDigest's rule. **Bulletproof keeps a `types/` folder; FSD calls `types` a bad name** and files types under `model` or `api`. Google prefers `interface` for object types, which conflicts mildly with the type aliases that `z.infer` produces ([Google TS Style Guide](https://google.github.io/styleguide/tsguide.html)).

## Logic lives in pure functions and hooks; server data lives in the query cache

**The consensus shape for a mid-sized app has three parts.** Pure functions hold domain rules. Custom hooks wire those rules to React state and server data. Components receive data and callbacks. react.dev frames hooks as sharing "stateful logic", not state, and warns against generic lifecycle wrappers like `useMount` ([Reusing Logic with Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)). Juntao Qiu's layered model is view → hooks → domain models → network gateway, with a strategy pattern for variant logic. It carries its own caveat: keep small, cohesive components together "so you don't have to look in multiple places" ([Qiu, martinfowler.com](https://martinfowler.com/articles/modularizing-react-apps.html)). Alex Bespoyasov's clean architecture adds use-case and port layers. He also lists the costs himself: more design time, more verbosity, harder onboarding ([Bespoyasov](https://bespoyasov.me/blog/clean-architecture-on-frontend/)). Practitioners criticise it as "overengineered complexity disguised as best practice" ([Medium opinion](https://medium.com/@mernstackdevbykevin/clean-architecture-for-frontend-sounds-smart-until-you-ship-62f9ccf54030)). DevDigest's client is thin over a Fastify API, so Qiu's hooks → gateway pair without a models layer is the proportionate reading. A domain folder earns its place only when non-trivial client rules appear.

Effects are the most common place where logic lands in the wrong spot. **"You don't need Effects to transform data for rendering", and you don't need them "to handle user events"** ([You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect)). The decision question is "Why does this code need to run?". A specific interaction belongs in an event handler. Synchronisation with an external system belongs in an Effect ([Separating Events from Effects](https://react.dev/learn/separating-events-from-effects)). TkDodo sharpens this: "Whenever a state setter function is only used synchronously in an effect, get rid of the state!" ([Don't over useState](https://tkdodo.eu/blog/dont-over-use-state)).

**The state-placement ladder is well supported:** derive the value during render, then local `useState`, then lift to the nearest common parent, then the URL for shareable filters, then context near its usage, and a global store only as a last resort. react.dev's structure rules (no redundant, duplicated or contradictory state; no mirroring props) anchor the bottom of the ladder ([Choosing the State Structure](https://react.dev/learn/choosing-the-state-structure)). Dodds anchors the colocation principle ([State Colocation](https://kentcdodds.com/blog/state-colocation-will-make-your-react-app-faster)). **Server cache and UI state are different kinds of state:** "We make a mistake when we combine the two" ([Dodds, Application State Management](https://kentcdodds.com/blog/application-state-management-with-react)). TanStack's docs show a global store shrinking from six fields to two (`themeMode`, `sidebarStatus`) once server data moves into Query. The same docs caution that Query "is not a replacement for local/client state management" ([TanStack: Does this replace client state?](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state)). The one sanctioned exception to "never copy server data into state" is a form's initial values, copied deliberately ([TkDodo, React Query and Forms](https://tkdodo.eu/blog/react-query-and-forms)).

**TanStack Query guidance has moved within the maintainer's own writing.** In 2020–2023 he recommended wrapping each query in a custom hook and keeping keys hierarchical and colocated with their feature through key factories ([Practical React Query](https://tkdodo.eu/blog/practical-react-query); [Effective React Query Keys](https://tkdodo.eu/blog/effective-react-query-keys)). By 2026 he writes: "Since v5, my preferred way to create Query abstractions is not with custom hooks anymore but with `queryOptions`". The reason is that options objects also work in prefetch calls, route loaders and event handlers, and callers compose them at the call site (`useQuery({ ...invoiceOptions(1), select })`) ([Creating Query Abstractions, 2026-02-23](https://tkdodo.eu/blog/creating-query-abstractions); [The Query Options API](https://tkdodo.eu/blog/the-query-options-api)). DevDigest's `lib/hooks/<resource>.ts` stays valid if each file exports a key factory and `xxxOptions()` alongside thin `useXxx()` hooks.

Next.js's own defaults point elsewhere. It recommends a server-only Data Access Layer, `import 'server-only'`, thin Server Actions that re-check authorisation, and choosing "one data fetching approach and avoiding mixing them" ([Next.js Data Security](https://nextjs.org/docs/app/guides/data-security)). TanStack advises new RSC apps to "avoid bringing in React Query until you actually need it", and never to render the same data in both server and client components ([TanStack Advanced SSR](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr)). **DevDigest's "all data through client TanStack hooks over an external API" is legitimate under the one-approach rule, but it is a project choice, not a Next.js default.** For global stores, the Redux style guide recommends feature-folder slices, events rather than setters, and keeping form state local ([Redux Style Guide](https://redux.js.org/style-guide/)). TkDodo prefers many small Zustand stores that export only hooks ([Working with Zustand](https://tkdodo.eu/blog/working-with-zustand)). Redux prescribes a single store, while TkDodo prefers many small ones, and that split is a genuine disagreement.

## Barrel files, naming and imports are where the experts split

| Question | Position A | Position B | Status for the skill |
|---|---|---|---|
| `index.ts` barrels in app code | Keep them as a public API: FSD (mandatory), Wieruch, Comeau ("~180 barrel files" of ~1,200 without trouble) | Remove them: TkDodo (11k → 3.5k modules, **68% fewer**), Hagemeister (10,000 modules ≈ 3.1 s load), Bulletproof, Vercel's `bundle-barrel-imports` rule | Ban aggregating barrels. A one-line per-component `index.ts` is a documented trade-off |
| Feature vs type folders | Feature/route slices: Bulletproof, FSD, Wieruch at scale | Type folders: Comeau | Size-dependent; hybrid by default |
| File-name case | PascalCase files: Airbnb (aged) | kebab-case everywhere: Bulletproof; snake_case: Google | Project convention (DevDigest: kebab `.ts`, PascalCase `.tsx`) |
| `enum` vs `as const` | `as const`: TS handbook, Pocock, `erasableSyntaxOnly` | `enum` allowed: Google | Prefer `as const` / `z.enum` |
| Import style | `@/*` alias: Bulletproof, Comeau | Relative within a project, with capped `../`: Google | `@/` alias, siblings relative |
| Where UI lives in Next.js | Inside `app/` under `_components`: Next.js strategy 3 | Outside `app/`: Bulletproof, FSD | Project convention |

**Barrels are the most consequential disagreement.** TkDodo measured the cost on a Next.js project: pages loading "over 11k modules, which took 5-10 seconds", cut "to about 3.5k modules - a reduction of 68%" once internal barrels were removed. He adds that "If you are writing app code, you're just making your life harder by putting `index.ts` files into arbitrary directories" ([TkDodo](https://tkdodo.eu/blog/please-stop-using-barrel-files)). Marvin Hagemeister shows module-loading cost growing with graph size and debunks the belief that modules load only on demand ([Hagemeister](https://marvinh.dev/blog/speeding-up-javascript-ecosystem-part-7/)). Next.js's `optimizePackageImports` fixes this only for listed third-party packages and is still experimental ([Next.js optimizePackageImports](https://nextjs.org/docs/app/api-reference/config/next-config-js/optimizePackageImports); [Shu Ding, Vercel](https://vercel.com/blog/how-we-optimized-package-imports-in-next-js)). FSD requires index files while conceding they cause circular imports and slow the dev server. It recommends one index per component in shared layers ([FSD public API](https://feature-sliced.design/docs/reference/public-api)). DevDigest's `index.ts` files each hold a single line, for example `export { AgentCard, AgentCard as default } from "./AgentCard";`, so importing one loads exactly one extra module and the graph-explosion argument barely applies. **The evidence-based rules are these:** no folder-level `_components/index.ts` that aggregates components, siblings import each other by file path rather than through `./index` (which avoids cycles), and no `export *` mixing server and client modules. No source measures the cost of single-re-export index files, so that gap stays open.

React's official naming rules are few and firm. Component names start with a capital letter. Hook names start with `use` plus a capital letter, and only functions that call hooks take that prefix ([Reusing Logic](https://react.dev/learn/reusing-logic-with-custom-hooks)). Handlers are named `handleX` and passed as `onX` props ([Responding to Events](https://react.dev/learn/responding-to-events)). Next.js reserves lowercase routing file names and the `_private` and `(group)` folder forms ([Next.js project structure](https://nextjs.org/docs/app/getting-started/project-structure)). Everything else about file case is convention. Bulletproof enforces all-kebab names with `eslint-plugin-check-file` ([Bulletproof project-standards](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-standards.md)). The same plugin can enforce DevDigest's hybrid with two globs. **No cited source covers boolean prefixes (`is`/`has`) or a one-letter `s` export from `styles.ts`.** Both are house conventions. Imports are ordered with `import/order` and `pathGroups` for `@/**` ([eslint-plugin-import order](https://github.com/import-js/eslint-plugin-import/blob/main/docs/rules/order.md)).

## Enforcement tooling turns placement rules into build errors

The skill describes where code goes. A linter is what makes that stick. **Bulletproof enforces its entire architecture with two rules.** The first is `import/no-restricted-paths`, configured with one zone per feature that bans cross-feature imports, one zone stopping features from importing `app`, and one stopping shared folders from importing features or `app`. The second is `import/no-cycle` ([Bulletproof .eslintrc.cjs](https://github.com/alan2207/bulletproof-react/blob/master/apps/nextjs-app/.eslintrc.cjs); [no-restricted-paths](https://github.com/import-js/eslint-plugin-import/blob/main/docs/rules/no-restricted-paths.md)). Those configs still use the legacy eslintrc format. As of 2026-09-27 the maintained options are these. `eslint-plugin-import` has about 69.7M weekly downloads, but its last release (2.32.0) dates from 2025-06-20. The faster fork `eslint-plugin-import-x` released 4.17.1 on 2026-06-28. `eslint-plugin-boundaries` 7.2.0 enforces rules between element types, entry points and private files, and needs a TypeScript resolver ([boundaries](https://github.com/javierbrea/eslint-plugin-boundaries); [jsboundaries.dev](https://www.jsboundaries.dev/)). **`dependency-cruiser` expresses "no cross-feature imports" as a single `$1` group-capture rule** instead of one zone per feature, and adds orphan and cycle detection ([rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)). Steiger is FSD's official linter, still in beta ([Steiger](https://github.com/feature-sliced/steiger)). Knip finds unused files and exports, and its Next.js plugin knows the App Router entry points ([knip Next.js plugin](https://knip.dev/reference/plugins/next)). ESLint's core `no-restricted-imports` matches import specifiers only and cannot tell where the importing file lives ([ESLint docs](https://eslint.org/docs/latest/rules/no-restricted-imports)). `next lint` was deprecated in 15.5 and removed in 16.0 in favour of the ESLint CLI with flat config ([Next.js 15.5](https://nextjs.org/blog/next-15-5); [Next.js ESLint](https://nextjs.org/docs/app/api-reference/config/eslint)). DevDigest's client has no ESLint dependency, config or lint script today, so any enforcement would be a new addition. The lowest-friction path is a flat `eslint.config.mjs` on `eslint-config-next` with no-restricted-paths zones and a cycle check.

For the skill's format, **Vercel's `agent-skills` is the strongest model.** Its SKILL.md is an index with prioritised categories, impact levels and rule IDs, and each rule has its own file with an Incorrect/Correct pair and a reference link ([vercel-labs/agent-skills react-best-practices](https://github.com/vercel-labs/agent-skills/tree/main/skills/react-best-practices)). **No official collection ships a React folder-organisation skill**, so the gap is real. Vercel's `composition-patterns` is the closest ([composition-patterns](https://github.com/vercel-labs/agent-skills/tree/main/skills/composition-patterns)); Anthropic's collection has none ([anthropics/skills](https://github.com/anthropics/skills)). Vercel retired `next-best-practices` because "Framework knowledge comes from the bundled docs, not from Skills", having found that "always-available context outperforms on-demand retrieval" ([vercel-labs/next-skills](https://github.com/vercel-labs/next-skills); [Next.js AI agents guide](https://nextjs.org/docs/app/guides/ai-agents)). The repo's local `next-best-practices` skill therefore looks like a stale copy that will receive no updates. Anthropic's authoring guidance sets the constraints. Write the description in the third person, covering what the skill does and when to use it. Keep SKILL.md under 500 lines, with references linked one level deep. Give a default rather than a menu of options. Build evaluations before writing extensive content ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [Claude Code Skills](https://code.claude.com/docs/en/skills)).

## Conclusion

The research changes what the skill should be. Its value does not lie in reproducing a canonical folder tree, because none exists. **It should be a decision procedure.** That procedure has four parts: colocate by default; promote only on real reuse, to the nearest common ancestor; keep imports one-way; and split on named triggers. Each step carries a clear marker separating cited rules from DevDigest's house conventions (the `_components/<Name>/` file set, the `styles.ts` → `s` export, kebab/Pascal file-name case, `lib/hooks` as the only data path). That separation is what keeps an agent from over-applying a convention to a different project, or treating an expert's opinion as law.

Two findings call for action beyond the skill text. The most load-bearing rules (no cross-feature imports, no aggregating barrels, no nested component definitions) are cheap to lint, and Vercel's evidence says always-loaded context beats retrieval. Those few rules therefore belong in `client/CLAUDE.md` and in a lint config, with the skill carrying the examples and rationale. The TanStack guidance has also moved toward `queryOptions` factories, so the `lib/hooks/<resource>.ts` convention should grow an options/key-factory export before the skill encodes "one hook per query" as settled practice.

### Which recommendations are project conventions, not universal rules

These DevDigest choices are defensible but have no A or B source mandating them, and the skill should mark them as house rules. They are: the per-component file set `Name.tsx` + `index.ts` + `constants.ts` + `helpers.ts` + `styles.ts` + `Name.test.tsx` (Comeau uses `Name.constants.ts`, FSD uses `config`/`lib`, and Bulletproof uses feature `utils`); the one-line `index.ts` per component, which contradicts TkDodo's blanket stance; `styles.ts` exporting a one-letter `s`; kebab-case `.ts` with PascalCase `.tsx`, which conflicts with Bulletproof's all-kebab rule and Google's snake_case; `app/**/_components` inside routes rather than outside `app/`; the central `src/lib/hooks/<resource>.ts` instead of per-feature `api/` folders; routing all data through client TanStack hooks rather than Server Components; the helper/util naming split; any numeric component-size limit; the choice of promoting on the second or the third use; and sharing one Zod schema between server and client forms, which is consistent with the sources but not prescribed by any of them. The rules that sources do support as general practice are: colocation and promotion on reuse; one-way dependencies with no cross-feature imports; no aggregating barrels in app code; no nested component definitions and pure components; `use` only for functions that call hooks, and `handleX`/`onX` handler naming; no Effects for derived data or event logic; no copying server state into React state (forms excepted); `as const` over `enum`; literal `process.env.NEXT_PUBLIC_*` access; and `'use client'` at subtree leaves with named exports instead of static compound subcomponents.
